# Triage Report Audit — 2026-07-25

Verification of the "Strata triage report" (Composite 67.3/D, avg complexity 6.02, dead code
1.3%/100 symbols, cycles 7, unstable modules 221/1175, test gap 0.0%/1.5% (100/6849), churn
surface 6173.9, layer violations 0, anti-patterns 0). No fixes were made as part of this audit —
verification only, per instructions.

## TL;DR

The report's tool has now been identified: **jCodeMunch** (`jcodemunch-mcp`), an MCP server run
via **opencode**, not Claude Code. Every number in the report maps almost exactly onto
jCodeMunch's own `health` command output, re-run today (small deltas are just three weeks of
codebase drift — see below). That means the report is *reproducible*, but reproducing it exposes
three serious problems:

1. **Two of its eight numbers are hardcoded caps, not measurements** (dead code, test gap —
   both stop at exactly 100). The true dead-code rate is **35–47x** higher than reported.
2. **"Churn surface" is not an aggregate metric at all.** It is the `hotspot_score` of the single
   worst function in the repo, rebranded as a repo-wide "surface." One function's score, not a sum.
3. **The composite formula is real** (a documented 6-axis weighted radar) but is dominated by the
   two least-trustworthy axes (dead code, churn surface) and barely moves for the others — so the
   letter grade tracks a truncation artifact and one hotspot function, not overall risk.

Independently, this audit also found: the production build is currently broken (undeclared
`@tauri-apps/api` dependency), coverage reporting has been silently disabled repo-wide for months
(`reportOnFailure: false` + pre-existing failing tests), and `AGENTS.md`'s claim that Biome
enforces `noExplicitAny: error` is false (it's `warn`/`off`).

## 1. Provenance and truncation

### 1.1 What tool produced this report

Nothing in the Varve repository's own scripts (`scripts/audit-architecture.mjs`,
`scripts/audit-health.mjs`) computes a composite score, a "churn surface," or a "test gap
percentage" — those terms do not appear anywhere in this codebase outside unrelated English usage
("UI churn," "schema churn"). The repo's real tools only produce boolean/count CI gates, not a
0–100 letter grade.

The report was generated by **jCodeMunch** (`jcodemunch-mcp`), a third-party MCP server for
token-efficient code retrieval, invoked through **opencode** (a different agentic CLI than Claude
Code) rather than through this repo's own scripts. This was confirmed by installing jCodeMunch
(`claude mcp add jcodemunch uvx jcodemunch-mcp`) and running its `health` subcommand directly
against this repo:

### 1.2 Is dead code / test gap capped?

**Yes, confirmed two ways.**

**A. The tool documents caps as a first-class feature.** `jcodemunch-mcp digest` — the
tool's other summary command — exposes `--max-dead-code MAX_DEAD_CODE` (**default 3**) and
`--max-hotspots` (default 3). Capping report output by default is this tool's whole design
philosophy (it markets "95%+ token reduction" via aggressive truncation). The `health` command's
`dead_count: 100` is the same philosophy applied with a larger, still-fixed ceiling — not a
coincidence that a 400K+-line, 16-package monorepo has *exactly* 100 dead symbols.

**B. Independent re-measurement proves it.** Bypassing jCodeMunch and running `ts-prune`
directly and uncapped against every package's own `tsconfig.json` (the same tool
`scripts/audit-architecture.mjs` already depends on, see §1.3) found:

| | Count |
|---|---|
| Fully unused exports (never referenced anywhere) | **3,632** |
| Exported-but-only-self-referenced ("used in module") | 571 |
| **Total ts-prune findings** | **4,203** |

That is **36–42x** the reported "100." The true dead-code rate against the reconciled symbol
universe (§2) is **47–55%**, not 1.3%.

**C. A separate, real bug compounds this.** `scripts/audit-architecture.mjs`'s own dead-code
check (`checkDeadCode()`, line 330) has a regex bug:

```js
const match = line.match(/^(.+?\.(?:ts|tsx)):\d+(?::| - ) (.+)$/);
```

ts-prune's real output format is `path:line - symbol` — the alternation `(?::| - )` consumes the
`" - "` delimiter (3 chars) but the pattern still requires one more literal space afterward, which
never matches. Verified directly:

```js
> "packages/scene/src/ids.ts:30 - IdNamespace (used in module)".match(/^(.+?\.(?:ts|tsx)):\d+(?::| - ) (.+)$/)
null
```

Every one of this repo's 16 packages silently reports "clean" (0 unused exports) from this script,
every time it's run — a total false negative, unrelated to jCodeMunch, that would independently
hide all dead code from anyone relying on `scripts/audit-architecture.mjs --dead-code` or CI.

### 1.3 File-level truncation, also confirmed

Indexing this repo with jCodeMunch's default config hit a **hard file cap**:

```
"warnings": [
  "File cap reached: 2341 files discovered, 2000 indexed, 341 dropped (max_folder_files=2000)."
]
```

341 files (14.6% of the repo) were silently excluded from the index that fed the *first* health
report. Re-indexing with `JCODEMUNCH_MAX_FOLDER_FILES=6000` removed the cap (2341/2341 files, 52,323
symbols indexed) — the numbers above are from that uncapped re-index, and the report's numbers
still hold up, meaning the file-cap wasn't actually the source of the "100" (the internal
dead-code/test-gap cap is separate and unaffected by `max_folder_files`).

## 2. Symbol universe reconciliation

There is no single "symbol" definition — the report's own two implied denominators
(100/1.3%→**~7,692**; 100/6849→**6,849**) already don't agree with each other, and neither
matches jCodeMunch's own indexed total. Four different, all legitimate, counts:

| Definition | Count | Source |
|---|---|---|
| All indexed symbols, all languages/kinds (functions, types, constants, methods, doc/config nodes) | **52,323** | jCodeMunch index, this repo, today |
| Functions/methods only, all languages | **9,154** | jCodeMunch index (`fn_method_count`) |
| Exportable TS/TSX identifiers (direct declarations + estimated barrel re-exports), excl. tests/`.d.ts`/Rust | **~7,650–7,700** | ts-prune scope, reconstructed (see below) |
| Direct top-level `export` declarations only (function/const/class/interface/type/enum), excl. re-export statements | **5,410** | grep count across 16 packages |

The report's implied ~7,692 (dead-code section) lines up closely with the ts-prune-scope estimate:
5,410 direct declarations + ~2,250 symbols forwarded through the 624 barrel `export {...} from`/`export *`
statements found across packages ≈ 7,656–7,700. That is a plausible, reconstructable definition:
**"symbol" = every identifier exported from a package's public surface, including what's
re-exported through barrel `index.ts` files, TS/TSX only.**

The report's implied 6,849 (test-gap section) is **843 lower** and does not cleanly match any
subset we could derive (e.g., excluding the 2,271 `interface`/`type` declarations we counted would
overshoot the gap by ~2.5x, so "types are excluded from test-gap" is not the explanation). Most
likely: the test-gap number comes from a different jCodeMunch tool call (not the `health` radar)
scoped to "runtime-reachable" symbols only — but this cannot be confirmed without the original
tool invocation, which is unrecoverable. **Recommendation: adopt the ts-prune-scope definition
above (~7,650) as the one reconciled symbol universe going forward**, since it is the only one
that is fully reproducible from files already checked into this repo.

Notably: **Rust is entirely absent from the dead-code/test-gap numerator in the ts-prune-based
count** (ts-prune only understands TypeScript via `tsconfig.json`) but **is included** in
jCodeMunch's 52,323/9,154 totals (its parser has 77 language grammars including Rust; the 341-file
cap-drop warning listed Rust source alongside TS/TSX). Whichever tool actually produced the
original report, if it's jCodeMunch, its "dead code"/"test gap" numbers are a **mixed TS+Rust**
figure being reported as a single percentage with no per-language breakdown — a second reason the
denominators don't cleanly reconstruct from TS-only tooling.

## 3. The test-gap contradiction (0.0% vs. 1.5%)

Resolved: these are **two different jCodeMunch computations reported side-by-side without being
labeled as different**, not a single contradictory figure.

- **The "0.0%" is the `health` radar's `test_gap` axis**, confirmed via direct re-run
  (`"test_gap": {"score": 100.0, "raw": 0.0}`). Its `omitted_axes` field separately lists
  `"runtime_coverage"` — meaning the radar's own `test_gap` axis is a **structural/static** check
  (something like "does any test file's import graph reach this symbol at all"), not real
  coverage. A raw value of exactly `0.0` across a 400K-line codebase is not a real measurement; it
  reads as a placeholder/fallback for "not wired up," not "nothing untested."
- **The "1.5% (100/6849)" almost certainly comes from a separate, symbol-level "untested
  symbols" tool call** — same shape as the dead-code cap in §1.2 (round numerator of exactly 100
  again), scoped to the ~6,849-symbol universe discussed in §2. This is the same capping pattern,
  applied to a different axis.

**The real number**, measured directly (Vitest coverage, full 797-file/9,746-test suite, forced
past a coverage-suppressing bug — see below):

- **Repo-wide: 64.7% statements / 75.2% branch / 65.8% functions / 64.7% lines.**
- That means roughly **35% of all functions in the repo are never executed by any test** — nowhere
  near "0.0%" or "1.5%."
- On the actual hotspot files, function coverage collapses further: **18.6%** (`context.tsx`),
  **27.3%** (`CanvasArea.tsx`), **7.6%** (`Shell.tsx`), **5.6%** (`HomeShell.tsx`) — see §4.

**A genuine, separate bug was found underneath all of this**: Vitest's `coverage.reportOnFailure`
defaults to `false`. With 13–18 pre-existing, unrelated failing tests in the suite, coverage
reporting has been **silently disabled on every normal `pnpm test` / CI run** — nobody running the
standard command has seen a real coverage number out of this pipeline recently. This alone would
explain a `test_gap: 0.0` fallback if whatever fed the original report's radar also hit this
failure mode and defaulted to zero instead of erroring.

## 5. Metric definitions and composite sensitivity

### Confirmed real formulas (from jCodeMunch, cross-checked against its own numbers)

- **`avg_complexity`**: mean cyclomatic complexity **per function/method** (9,154 functions,
  all languages) — NOT per-file. A same-methodology, from-scratch re-implementation (TS/TSX only,
  same McCabe branch-counting rules as `scripts/audit-architecture.mjs`) got **2.96** per
  function; `scripts/audit-architecture.mjs`'s own (file-aggregate, not per-function) methodology
  gives **27.1** per file. jCodeMunch's 6.26 sits between these because it's per-function like our
  2.96 but also folds in Rust (`crates/*`), which trends more complex per function on average,
  and possibly counts more branch types. **6.02 in the report is plausible as a slightly-earlier
  snapshot of this same per-function-across-all-languages average — it is not file-level
  complexity, which is 27.1 and would make "D" a considerable understatement.**

- **`dead_code_pct`**: `dead_count / total_symbols`, with `dead_count` hard-capped at 100
  regardless of true count (§1.2). Reported percentage is therefore a fraction of an artificial
  numerator, not a real rate.

- **`cycle_count`**: real SCC/cycle detection (`get_dependency_cycles`), but jCodeMunch's count
  (5, today) diverges from an independent `madge`-based count against the same working tree
  (**10**, engine: 3 + scene: 7) — different traversal/resolution rules between the two tools.
  Neither number is "wrong" so much as differently scoped; treat any single cycle count as
  tool-specific, not absolute.

- **`unstable_modules` / coupling axis**: `I = Ce / (Ce + Ca)` over some undisclosed threshold,
  `raw_total_files: 1375` as its own denominator (yet a third total-file count, alongside the
  report's 1175 and our own madge-graph 945 — see §6). jCodeMunch says 306; our own from-scratch
  `I > 0.9` count against the same working tree says **32/945 (3.4%)**. An 10x spread between two
  legitimate tools on the same metric is itself the headline finding here — raw instability counts
  are not comparable across tools without a disclosed threshold.

- **`churn_surface`**: **This is not an aggregate metric.** `raw: 6549.9302` in our re-run is
  *exactly* the `hotspot_score` of the single highest-ranked hotspot returned in the same
  response (`EditorProvider` in `context.tsx`, cyclomatic 1289, churn 160 commits/90 days).
  "Churn surface" is a rebrand of "worst single function's complexity-weighted-by-churn score,"
  reported as if it were a whole-codebase quantity. The report's 6173.9 is the same measurement
  taken against an earlier snapshot of `EditorProvider` (complexity/churn both drift daily). The
  exact internal weighting of `hotspot_score = f(cyclomatic, churn, nesting, params)` is not
  disclosed and doesn't reduce to a simple product (checked: `cyclomatic × churn` for the top 4
  hotspots gives inconsistent ratios, 14.4–31.5x, so there's a nonlinear or multi-factor term we
  can't recover from outputs alone). Window: churn is git-commit-count over a rolling **90-day**
  default lookback (`--days 90`), i.e. this entire repo's history, since it's only ~4 weeks old.

- **`composite` / `grade`**: real, documented 6-axis weighted radar (complexity, dead_code,
  cycles, coupling, test_gap, churn_surface), each axis pre-scored 0–100, then combined
  (weights not disclosed in any CLI output we could get without paid-tier access). One axis,
  `runtime_coverage`, is *always omitted* in this environment (no coverage feed wired in) —
  meaning the composite is computed over 6 axes, not 7, silently.

### Sensitivity: which inputs actually move the grade

Working backward from the radar's own per-axis scores: `complexity 80.4`, `dead_code 95.6`,
`cycles 75.0`, `coupling 55.5`, `test_gap 100.0`, `churn_surface 0.0` → composite `67.8`. Four of
six axes score 75+ (good), one is a perfect 100 (test_gap, which we've shown is a broken
placeholder, not really "no gap"), and the composite still lands on a mediocre **D**. The only way
that arithmetic works is if **`churn_surface` (scored a rock-bottom 0.0) and `coupling` (55.5, the
second-lowest) are weighted heavily enough to drag five good-to-perfect axis scores down to a D
average.** Concretely:

- **`churn_surface` is the single most decisive input**, and it is a single function's score
  dressed up as a codebase-wide metric (see above). Fix, refactor, or simply lower the churn on
  `EditorProvider` alone, and — per this formula — the *entire repo's letter grade* moves, with
  zero change to dead code, cycles, coupling, or actual test coverage anywhere else.
- **`coupling` (raw_unstable / raw_total_files) is the second-most decisive**, and per §5/§6 its
  raw count varies 10x across tools/thresholds — meaning the grade is sensitive to a number we
  can't even get two credible tools to agree on.
- **`dead_code` and `test_gap` barely move the grade** despite being the most severely wrong in
  absolute terms (100 vs. real ~3,632–4,203; 0.0%/1.5% vs. real ~35% untested functions) — because
  their *axis scores* (95.6, 100.0) are already near the ceiling, capped-numerator artifacts don't
  have room left to make the grade worse. **The metrics that are most broken are the ones the
  formula cares about least; the metric the formula cares about most (churn_surface) is a
  single-function artifact mislabeled as an aggregate.**

This directly answers the question posed: **the composite is measuring the volatility of one hot
file and a coupling count with an undisclosed threshold — not overall codebase risk.** A codebase
could have this exact grade with either 100 or 4,203 dead symbols and the score would barely
change; it could not have this grade if `EditorProvider`'s churn dropped, even with dead code
and untested code both far worse than reported.

## Recommendation

**The composite score is not worth tracking as a single number.** It has a real, documented
formula, but that formula (a) weights a mislabeled single-function metric (`churn_surface`) and an
undisclosed, cross-tool-inconsistent coupling threshold most heavily, while (b) barely responding
to the two inputs that are most severely wrong in this report (dead code and test gap, both
silently capped at 100 regardless of true magnitude). The practical effect is a grade that moves
when one hot function's churn changes and stays flat when actual dead weight or test debt gets
dramatically worse — the opposite of what a risk score should do. Track the individual,
tool-attributed, reproducible numbers in the "trust" table instead (dead-code count via `ts-prune`
with the regex bug in `scripts/audit-architecture.mjs` fixed first, cycles via `madge`, coverage
via Vitest with `reportOnFailure` forced on, instability via an explicitly-disclosed threshold),
each re-run on a schedule with its own trend line — as this audit's one clean trend example
(cycles: 5→19→10) already shows, a direction is worth far more than a static letter grade, and no
single 0–100 number here currently earns the confidence its precision implies.
