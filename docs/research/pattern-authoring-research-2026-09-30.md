# Pattern authoring research (2026-09-30)

This note records focused product and renderer evidence used to guide Varve's
pattern-authoring work. Issue reports are individual, version-specific reports;
they do not establish how common a problem is or prove the same defect exists
in Varve.

| Source and version | Finding | Varve decision | Acceptance check |
|---|---|---|---|
| [Adobe Illustrator: Create and apply patterns](https://helpx.adobe.com/illustrator/using/create-edit-patterns.html), help updated 2026-08-31 | Selected artwork can become a pattern through a dedicated make/edit flow; new patterns enter Swatches and editing an existing swatch updates its definition. | Keep source editing distinct from a fill instance. Preserve the selected artwork, expose definition scope and usage, and put reusable definitions in the existing library surface. | Create from selection leaves originals intact; edit one shared definition and confirm every linked use changes; Make Unique isolates one use. |
| [Adobe Photoshop: Create a new pattern](https://helpx.adobe.com/photoshop/using/pattern-preview.html), help updated 2026-02-23 | Pattern Preview repeats artwork outside the canvas, with the documentation recommending Smart Objects for the workflow. | Show neighboring cells while editing, but keep preview copies as view state rather than scene objects. | Edge and corner edits update neighboring previews without increasing source-node count or creating extra history entries. |
| [Inkscape report #5971](https://gitlab.com/inkscape/inbox/-/issues/5971), reported against Inkscape 1.1.1 (2021) | A user reports pattern transform handles can be far from the filled object, dragging is hard to reproduce, and transparent pattern color is awkward. | Keep transform handles near the edited fill and offer numeric controls and transparent backgrounds. | Keyboard and numeric transform edits work in a compact inspector; handles remain visible after zoom and selection changes. |
| [Inkscape report #1018](https://gitlab.com/inkscape/inkscape/-/issues/1018), Inkscape 1.1 development build (2020) | A user reports zooming a patterned object caused very large memory growth and a black canvas; the discussion identifies zoom-sized intermediate tile surfaces as a risk. | Bound surface bytes and repetition work by visible bounds and effect influence; do not allocate an entire destination-sized pattern field for a swatch or preview. | Dense-repeat and zoom tests stay within configured surface and instance budgets and return an explicit preview/export limitation instead of partial output. |
| [resvg report #882](https://github.com/linebender/resvg/issues/882), opened 2025-02-10 and still open on 2026-09-30; related [tiny-skia report #83](https://github.com/linebender/tiny-skia/issues/83) | Replies confirm a pattern shift that changes at zoom/output-size thresholds and with fractional transformed tile sizes; the maintainer identifies the behavior as a bug. | Preserve fractional authored geometry and validate SVG output at several output sizes and scales. Compare independent renderers; do not treat a successful browser preview as proof of export parity. | Render the same fractional pattern at adjacent output widths and multiple scales; verify phase stability against Varve's source geometry and document renderer-specific differences. |
| [resvg report #628](https://github.com/linebender/resvg/issues/628), opened 2023-05-21, labelled blocked | The report says the tiny-skia path accepts only integer tile offsets and points to upstream subpixel-offset support. | Keep fractional phase in the source model. Where a target renderer cannot preserve it, report the output limitation or choose a tested faithful fallback. | Fractional and negative phase property tests plus exported-pixel comparisons detect rounding drift. |
| [Inkscape report #3807](https://gitlab.com/inkscape/inbox/-/issues/3807), Inkscape 1.0.1 (2020) | A user reports a pattern visible in the editor disappearing from some PNG exports. | Treat export as a separate acceptance surface; resolve every source before encoding and never report a missing-resource fallback as successful artwork. | Export each reference pattern through the UI, decode the PNG, and verify non-background pattern pixels and source dependencies. |
| [MDN SVG `<pattern>` reference](https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Element/pattern), referencing SVG 2 | `patternUnits` defines the coordinate system for tile `x/y/width/height`; `patternContentUnits` defines content coordinates; `patternTransform` maps pattern coordinates to the target. `viewBox` changes the content relationship. | Serialize each coordinate relationship deliberately; do not substitute one attribute for another. Use safe, remapped IDs and resolve inherited `href` definitions on import. | Inspect emitted SVG and render it in at least two independent implementations; cover user-space and object-bounds cases, transforms, and inherited definitions. |

## Limits and scope

- These sources motivate concrete tests, not claims that every renderer or
  application has the same failure.
- Varve can import or replace a raster tile and show its repeated preview.
  Seam inspection and offset repair remain unimplemented; wraparound brush
  behavior is not claimed.
- Hexagonal, mirrored, and staggered arrangements ship only where the shared
  evaluator and export path agree on a finite, tested repeat cell.
