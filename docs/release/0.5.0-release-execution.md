The [next resume](https://github.com/K-Arthur/varve/actions/runs/37507587682)

Windows ARM64 passed the formatter probe, then exposed a second native build
defect: `diffusion-rs-sys 0.1.20` hardcodes `cl.exe` for all MSVC targets while
its bundled GGML ARM backend explicitly requires Clang. Workflow-pinned build
tooling now selects the runner's LLVM `clang-cl` through `CMAKE_TOOLCHAIN_FILE`,
overriding those explicit defaults without editing tagged product source.
It selects the portable ARMv8-A CPU baseline rather than runner-specific
instructions. An early native C/C++ compile/link/execute probe checks ARM NEON,
the Windows SDK and the actual ARM64 PE machine type before expensive builds.
The local regression fixture executes CMake's actual cache overrides; it does
not establish that the production ARM64 build passed. That hosted build and
all installed-production checks remain pending.

In [37510285894](https://github.com/K-Arthur/varve/actions/runs/37510285894),
the actual ARM64 Clang C/C++ compile/link/execute probe passed. The subsequent
Rust build selected Git Bash's POSIX `link.exe` instead of Microsoft's linker:
the environment setup exported the complete PATH through `GITHUB_PATH`, which
changed its precedence. The setup now exports only its build-tool directories
and binds Cargo to the absolute native ARM64 Microsoft linker. A separate
offline Cargo probe compiles a host build script and ARM64 executable in the
same Bash shell as the production build, before dependency installation.

Successful bundle targets now proceed to their owning installed qualification
even if another bundle fails. Every cell still selects its own unique successful
producer and verifies tagged bytes; the failed target fails selection. Final
trust still requires the complete bundle and native qualification jobs. This
collects independent platform failures without allowing a partial release.

In [37512334886](https://github.com/K-Arthur/varve/actions/runs/37512334886),
both native compiler/linker probes passed, and production compilation passed
the previous failures. GGML then reached C++ sources that use exceptions;
Clang's MSVC-compatible driver requires `/EHsc`, absent from the dependency's
explicit flag override. The ARM64 toolchain now enables that standard exception
model, and its early C++ probe actually throws and catches an exception before
running its ARM NEON check. The four successful platform packages proceeded
to their independent native qualification jobs. Both Linux clean DEB/RPM
container checks passed. Linux installed-app sessions then failed capability
matching before app launch: the pinned external driver forwards the invented
`browserName: wry` unchanged, while WebKit rejects it. The adapter now leaves
browser selection to WebKit and preserves the exact executable/document args.
A regression check captures the actual adapter configuration and sends it
through the frozen WebdriverIO HTTP transport.

Windows x64 installed the verified published 0.2.1 payload but failed CDP
readiness. [Microsoft documents elevated WebView2's override restrictions](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security#for-an-elevated-host-app-use-appropriate-override-flags):
the current runtime ignores the environment-based debug port and profile.
Qualification now sets Varve-specific HKLM browser arguments and user-data
folder on disposable GitHub-hosted runners, retaining/restoring prior values
and types in `finally`. It exposes only a loopback endpoint during the test;
no product flags, wildcard policy or runtime downgrade is shipped. Native
hosted execution is still required to verify this repair.

Native qualification now checks out its complete adapter closure from the
workflow SHA, alongside the certified product checkout. Session wrappers
resolve adjacent adapters from their own directory. The published baseline,
input document fixture, installed 0.5.0 bytes and frozen automation dependency
versions remain product-pinned. This avoids rerunning old tagged harness code
after a master-only repair. macOS qualification is still collecting evidence;
no installed functional check has been claimed as passed.

The macOS seed had not launched after several minutes: the memory guard
reported 871 MB using raw free pages. Its macOS sampler now uses Apple's
read-only `memory_pressure -Q` kernel headroom percentage, retaining the same
1536 MB floor and a conservative free-page fallback if querying fails.
[Apple's implementation](https://github.com/apple-oss-distributions/system_cmds/blob/main/memory_pressure/memory_pressure.c)
returns after reporting when no pressure-generation option is specified.
CLI regression fixtures prove admission/rejection for healthy, pressured,
invalid and unavailable native query results. The repaired guard is part of
the workflow-pinned qualification closure; no memory gate is disabled.

In [37516903120](https://github.com/K-Arthur/varve/actions/runs/37516903120),
the native probes and complete helper/application compilation passed the previous
failures. Final DLL linking then failed with `LNK1158: cannot run mt.exe`: only
the LLVM/MSVC directories had survived into the Bash build shell, omitting the
Windows SDK manifest tool. [Microsoft documents that LINK locates this helper
through its directory or PATH](https://learn.microsoft.com/en-us/cpp/error-messages/tool-errors/linker-tools-error-lnk1158?view=msvc-170).
Setup now resolves `mt.exe` and `rc.exe` in the imported developer environment,
verifies their SDK ownership, and retains only their tool directories. The
offline Rust probe builds a native library and executable with the actual
product manifest embedded, in the same Bash shell as production. This must
pass on the hosted ARM64 runner before the next production build; no manifest
or tagged product source is removed to bypass linking.

The failed build also exposed ineffective caching: the app is a standalone
Cargo workspace at `apps/desktop/src-tauri`, while the cache selected only the
root `target`; failed jobs did not save completed dependency compilation.
Bundle caching now includes both workspace target directories, retains
dependencies after a later failure, and keys the ARM64 toolchain's contents in
addition to the action's Rust/compiler/environment/lockfile keys. [The pinned
cache action documents these inputs and its dependency-only cleanup](https://raw.githubusercontent.com/Swatinem/rust-cache/6323deb102c322ba6fcbdcafc7e3dddab59af2b6/README.md).
Installed product binaries are still rebuilt and independently qualified;
no timing improvement is claimed before hosted cache evidence exists.

## Website and installed-release acceptance

Until the actual release is published and verified, the public download page
correctly continues to advertise `0.2.1`. Do not hand-edit the generated
website manifest or advertise draft assets. Publication must refresh the
verified release data, deploy the exact-source website/demo, and verify live
download links, hashes, version labels, mobile layout and feature availability.

Package acceptance requires the installed-production gates described in the
[candidate runbook](release-candidate-runbook.md): the published 0.2.1 file
seed, same-profile upgrade, save/reopen, editing/undo, and actual PNG/SVG/PDF
exports on the release platforms. Checksums, SBOM, provenance, attestation,
signing status and updater availability remain required on the uploaded bytes.

The [complaint-informed research](../research/design-tool-failure-modes-2026-10-02.md#release-acceptance-follow-up-2026-10-06)
connects file corruption, indefinite saving and AppImage installation failures
to these acceptance checks and truthful website guidance.
